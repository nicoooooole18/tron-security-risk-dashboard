# AI 预评审报告：JustLend USDT 黑名单监控与 SEV-2 告警

## 结论

需求方向合理，能够承接现有研究文档中识别出的核心风险：USDT 黑名单地址可能通过 JustLend 清算、赎回、抵押品迁移等路径完成经济价值转移。当前需求已经具备产品化基础，但逻辑闭环仍不完整，主要缺口集中在地址池口径、黑名单状态、触发时序、估值规则、告警处置和证据留痕。

当前不建议直接进入开发，应先补齐 P0 规则后再写正式 PRD 或技术方案。

## 🔴 P0 — 必须解决

- 监控地址池与清算告警口径存在断点 — 来源：产品 / 开发
  影响：当前地址池只覆盖持有 `jUSDT`、`jUSDD` 或借款 `USDT`、`USDD` 的地址，但 SEV-2 又要求覆盖 `liquidator` 和 `liquidated_user`，可能漏掉不在持仓/借款池内的黑名单清算人。
  建议：拆分 `风险敞口地址池` 与 `清算参与地址池`；每日扫描覆盖敞口地址，清算事件触发时实时或准实时检查 `liquidator`、`liquidated_user` 黑名单状态。

- 黑名单状态口径不闭环 — 来源：开发 / QA / 产品
  影响：只拉 `AddedBlackList` 会误报已被移除黑名单的地址，也无法区分历史风险与当前风险。
  建议：同时维护 `blacklist_event` 与 `blacklist_status_snapshot`，纳入 `AddedBlackList`、`RemovedBlackList`、`DestroyedBlackFunds` 和 `getBlackListStatus(address)`。

- SEV-2 触发时序未定义 — 来源：产品 / QA
  影响：无法判断清算或迁移必须发生在黑名单之后，还是历史行为也算，容易误报或漏报。
  建议：主规则定义为“地址进入黑名单后发生清算或大额迁移触发 SEV-2”；黑名单前行为只作为关联证据，不单独触发。

- 大额抵押品迁移缺少可执行技术定义 — 来源：开发 / QA
  影响：`redeemUnderlying`、jToken `Transfer`、底层资产转账、DEX 兑换可能重复计数或漏算，10 万美元阈值无法验收。
  建议：建立 `collateral_movement_fact`，明确 movement_type、asset、amount、usd_value、from、to、market、source_tx、是否计入 24h 累计窗口。

- USD 估值规则缺失 — 来源：开发 / QA
  影响：jUSDD、jBTT、jwstUSDT 等不能直接按 token 数量判断是否达到 `100,000 USD`。
  建议：定义公式：底层资产数量 = jToken 数量 × exchangeRate；USD 价格取触发区块最近可用价格；价格缺失进入“待估值”，不直接视为无风险。

- 告警处置闭环缺失 — 来源：产品 / 设计 / UX
  影响：SEV-2 只停留在通知层，无法证明平台已完成合理风控响应。
  建议：定义状态机：`待核查`、`核查中`、`已确认风险`、`误报/无需处理`、`已关闭`、`重新打开`；记录处理人、时间、备注和证据快照。

- 后台 IA 与证据链页面未定义 — 来源：设计 / UX
  影响：用户能看到风险，但无法完成“发现 -> 判断 -> 核查 -> 处置 -> 留痕”。
  建议：定义四个核心页面：风险概览、黑名单命中列表、SEV-2 告警列表、地址风险详情；详情页展示黑名单主体、角色关系、清算记录、迁移路径、证据时间线和处置记录。

## 🟡 P1 — 建议优化

- 历史回溯、每日扫描、SEV-2 告警三类产物未区分 — 来源：产品
  建议：历史回溯输出“风险基线报告”，每日任务输出“新增/持续命中列表”，SEV-2 输出“需响应告警”。

- 每日扫描与 SEV-2 时效不匹配 — 来源：开发
  建议：采用“事件监听近实时告警 + 每日对账补偿”模式；每日扫描用于兜底，SEV-2 由事件流尽量实时触发。

- 关联清算规则仍需分层 — 来源：产品 / QA / 开发
  建议：MVP 先做直接规则：黑名单地址作为 `liquidator` 或 `liquidated_user`；增强规则再加入一跳/二跳资金关系、连续清算、清算后资产回流等关联图谱。

- 迁移资产范围需明确 — 来源：产品 / QA
  建议：筛选入口是 USDT / USDD 风险敞口，但迁移监控覆盖 JustLend 抵押品相关资产，不限于 USDT / USDD；MVP 至少覆盖赎回、转出、一跳跨地址迁移。

- 告警去重和合并规则缺失 — 来源：开发 / QA
  建议：定义去重 key：`blacklisted_address + trigger_type + role + window_start + primary_tx_hash`；24h 累计迁移合并为一条告警，但保留交易明细。

- 任务完整性标准缺失 — 来源：QA / 开发
  建议：每日任务输出扫描区块范围、地址池数量、事件数量、状态查询成功率、失败重试次数、缺失地址数；任务失败应触发运维告警。

- 权限和审计要求缺失 — 来源：QA
  建议：查看、导出、关闭告警、修改阈值、标记误报设置不同权限；所有操作写审计日志。

- 告警文案存在合规过度定性风险 — 来源：QA / UX
  建议：统一使用“USDT 黑名单命中地址”“疑似通过关联清算迁移价值”“需人工核查”，避免写成未经证实的法律事实。

## 🟢 P2 — 锦上添花

- 增加风险分层 — 来源：产品 / QA
  建议：仅黑名单命中为“观察”，有敞口但无清算/迁移可为 SEV-3，组合风险为 SEV-2。

- 增加证据包导出 — 来源：开发 / UX
  建议：每条 SEV-2 支持导出 evidence bundle，包含黑名单事件、清算交易、迁移交易、估值依据、任务版本、人工处理记录。

- 增加样例与反例 — 来源：QA
  建议：用 `TLfa...eusu` / `TRq3...dURa` 构造正例，补充普通清算人、已移出黑名单地址、低于 10 万 USD 迁移地址作为反例。

- 增加指标看板 — 来源：产品 / QA
  建议：展示当前黑名单命中地址数、仍有敞口地址数、24h 新增 SEV-2、累计迁移金额、待处理告警数、平均响应时长。

## 建议下一步

先补齐 P0 后生成正式 PRD。优先确认：

1. 风险敞口地址池与清算参与地址池的完整合约清单。
2. 黑名单历史状态与当前状态的数据模型。
3. SEV-2 触发时序和去重规则。
4. 抵押品迁移事件集合与 USD 估值公式。
5. 告警状态机、处理 SLA、权限与审计规则。
